# 阶段 3：概要设计

**技能**：`hld-design`（安全侧配 `threat-model`）｜ **产出**：`dev/design/*概要设计*.md` + `dev/design/威胁模型-*.md`

## 做什么
从 SRS 推导系统总体架构：分层、模块划分、模块间依赖与调用关系、技术选型、部署拓扑、
非功能设计（性能/安全/可用性/日志监控）。

## 要点
- **技术选型在这一阶段定死**：阶段 7 走深度档时，`dev-fullstack-product` 的阶段 1 技术栈确认
  应当**读本文档已定的选型**，只补它没覆盖的项，不要推翻重选
- 架构图、部署图、模块依赖图一律走 `diagram-generator`
- 老项目架构既定 → 用 `hld-design` 的**反向同步模式**从代码补文档

## 威胁建模（`threat-model`，阶段 3 收尾时做）

拓扑一定下来就做，**结论是阶段 4 的输入**：数据流与信任边界 → 逐边界过 STRIDE →
每条威胁配「可验证的缓解措施 + 测试用例编号」→ 高可能性×高影响项回写进详细设计的
**接口鉴权列、数据范围列、表结构约束**与 SRS 非功能章节。

可跳过：纯内部工具、无多租户、无敏感数据、不对公网暴露 —— 跳过要在进度存档里写明理由。
**不可跳过**：有付费/资金流、多租户或多角色权限、处理个人信息、有文件上传或第三方回调。

写完代码后的静态安全审计是阶段 11 的 `pm-ai-ship-audit`，它会反过来核对「威胁模型里的缓解，代码做没做」。

## 门禁（进阶段 4 前）
- [ ] 威胁建模的高×高项都有缓解措施与回写位置，残余风险有确认人（跳过时注明理由）
- [ ] 模块划分清晰，每个模块的职责边界写明
- [ ] 技术选型每项带版本号（不写 `latest`）
- [ ] 与 SRS 的非功能需求逐条对应
