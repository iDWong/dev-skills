# 专家评审（阶段 5）

## 0. 规则

- 12 类角色**全部覆盖**，每个角色至少 **3 条具体意见**
- 意见必须**指到实处**：文件路径（`src/x/y.ts:42`）、页面名、接口路径、配置项。
  「代码质量尚可」「建议加强安全性」这类空话**不算一条意见**
- 每条意见给：**结论（符合/不符合）+ 证据 + 整改建议 + 严重级**
- 不符合项**当场整改**，回填闭环状态；全部闭环才进阶段 6

## 1. 评审矩阵

| 角色 | 评审重点 | 具体检查项 |
|---|---|---|
| 高级开发工程师 | 代码质量、架构合理性、可维护性 | 分层是否清晰、重复代码、异常处理、命名、圈复杂度、依赖方向 |
| 高级测试工程师 | 用例覆盖度、缺陷质量、回归有效性 | 用例是否覆盖边界与异常、缺陷复现步骤是否可用、回归是否验到关联路径 |
| 高级产品经理 | 功能与 SRS/PRD 一致性、交互闭环 | 逐条对功能清单打勾、每条流程能否走完、空态/失败态有没有出路 |
| 产品总监 | 产品定位、商业价值、优先级合理性 | 做的是不是核心价值、有没有把资源花在边缘功能上 |
| 项目经理 | 里程碑、风险、资源、进度 | 阶段产出是否齐、风险是否有应对、遗留项是否有主人 |
| 项目总监 | 项目整体健康度、跨端协同 | 三端进度是否匹配、接口契约是否一致、联调阻塞点 |
| 高级 UI/UX 设计师 | 视觉还原度、交互细节 | 逐页对设计稿：色值/字号/间距/圆角/图标/八种状态 |
| UI/UX 设计总监 | 设计系统一致性、体验创新 | 同类组件是否同一套规范、深浅色主题、无障碍对比度 |
| 高级运维工程师 | 部署脚本、监控、容灾、可观测性 | 一键部署是否真能跑、日志是否结构化、健康检查、备份与回滚 |
| 运营总监 | 运营后台可用性、数据看板、活动配置能力 | 常用操作点击层级、批量操作、导出、权限粒度、指标口径 |
| 全栈开发专家 | 前后端协同、性能瓶颈、技术选型 | N+1 查询、请求瀑布、大列表渲染、缓存策略、包体积 |
| 技术 CTO | 技术战略、扩展性、成本、长期演进 | 是否过度设计、是否欠设计、云成本、团队可接手性、锁定风险 |

## 3. 自我反驳（写报告前做一遍）

对每条「符合」结论问一句：**我真的看过对应的代码/页面吗，还是在假设？**
没看过就去看，或把结论降级为「未核查」。评审报告里出现没核查过的「符合」，
比不做评审更有害——它会让人以为这块已经验过。
