# 回滚操作手册模板（填空即用）

## 1. 数据可逆性：expand-contract 三步法

| 步 | 做什么 | 这一步能不能回滚 | 发布次数 |
|---|---|---|---|
| **expand（加）** | 只做加法：新增列/表、新增索引、开始双写；新列可空或有默认值 | ✅ 可以，直接回代码即可（新列留着不影响旧代码） | 第 1 次 |
| **migrate（迁）** | 回填历史数据、把读切到新列、校验两边一致 | ✅ 可以，把读切回旧列 | 第 2 次 |
| **contract（收）** | 停双写、删旧列/旧表 | ❌ **不可逆** —— 必须先确认新链路稳定运行一个完整周期 | 第 3 次，单独发 |

**反例**（最常见的事故）：同一次发布里「改列名 + 改代码」。回滚代码后数据库已经是新列名，旧代码起不来，
于是只能硬着头皮往前修——这就是没有回滚方案的典型成因。

**迁移脚本的硬要求**：可重复执行（跑两次不报错）、有对应的 `down`／补偿脚本、回填分批且可中断续跑。

## 2. 回滚决策树

```
发现异常
├─ 命中自动回滚阈值（5xx / 数据错误 / 核心链路不可用）
│    └─ 立即回滚，不讨论。事后复盘
├─ 只影响新功能，且有开关
│    └─ 关开关（秒级）→ 观察 10 分钟 → 仍异常则整体回滚
├─ 影响面可控、非核心
│    └─ 值班人 + 负责人两人确认 → 修前滚 or 回滚
└─ 分不清影响面
     └─ 按"影响面未知 = 影响面最大"处理，先回滚
```

## 5. 常踩的五个坑

1. **配置旧值没记**：回滚代码容易，回滚配置靠回忆——发布前把旧值抄进变更清单
2. **前后端单端回滚**：契约变了却只回一端，另一端直接 400/500
3. **迁移脚本没有 down**：写 `up` 时顺手写 `down`，哪怕 `down` 只是一句「不可逆，见补偿脚本」
4. **开关默认开**：等于没有开关，出事只能整体回滚
5. **回滚后不验证**：以为切回去就好了，实际上缓存里还是新数据格式——回滚后必须跑冒烟用例
